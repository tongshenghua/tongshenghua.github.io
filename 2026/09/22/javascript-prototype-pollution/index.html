这篇文章就是讲清楚：这件事是怎么发生的。

一、两条必须记住的规则

原型污染的入门资料通常会把 JavaScript 的原型链从头讲一遍。这里不重复，只挑两条真正被利用的规则——其余的都可以之后补。

规则一：属性查找会沿着原型链往上走

访问 obj.x 时，JavaScript 先看 obj 自己有没有 x。没有，就去看 obj 的原型，再没有就继续往上，直到 Object.prototype（链的顶端）为止。

这条链的顶端是共享的。所有普通对象最终都指向同一个 Object.prototype，所以往链顶写一个属性，等于给程序里每一个对象都加了这个属性。

在浏览器控制台里跑这三行，就能亲手验证：

b 从头到尾没见过 a，却读到了 a 写进去的值。这就是原型污染的最小复现。

规则二：JSON.parse 造出的是「自有属性」

这一条是整篇文章最关键的细节，也是最容易被忽略的。

两种写法看起来只差一个 JSON.parse，结果完全不同。

原因在于：o1.__proto__ = {...} 触发的是原型链上那个 setter，它的语义是「把我这个对象的原型换成新对象」——这是一个正常操作，不会影响到别人。

而 JSON.parse 走的是内部的 [[DefineOwnProperty]]，它绕过 setter，直接在对象上创建了一个名为 __proto__ 的、可枚举的自有属性。于是：

  • for (let key in o2) 会遍历到 key === "__proto__"
  • o2["__proto__"] 拿到的是那个自有属性 {x: 1}，不是 Object.prototype

二、三种利用形态

原型污染本身不直接等于漏洞，它需要和一个**下游的消费点（sink）**配合。根据 sink 的不同，危害分成三类。

值得注意的细节：这条 payload 里并没有出现 __proto__，写的完全是目标对象自己的属性。

这其实提醒我们一件事：「能写到任意路径」本身就已经是漏洞了，不需要等到污染原型才算数。很多资料把这类问题统称为原型污染，但严格说，它和「改写 Object.prototype」是两种不同的原语——前者影响一个对象，后者影响整个进程。后面两种才是真正的原型污染。

三、为什么自动化工具很难发现它

这一类漏洞几乎不可能靠模式匹配扫出来，原因有三层：

第一，漏洞代码本身完全合法。 merge(to, from) 这行代码没有任何特征。同样一个函数，用在配置合并上是安全的，用在用户输入上就致命——工具无法从这个函数本身判断语境。

第二，问题的本质是数据流，不是语法特征。 SQL 注入有拼接模式，eval 有明确关键字。而原型污染问的是「用户可控的字符串，最终有没有走到属性名的位置」——这是一个跨文件的数据流问题。攻击者控制的不是值，是 key。

第三，source 和 sink 可能隔着很远。 在这篇文章的例子中，_.set 在路由文件里，触发 XSS 的 EJS 模板在另一个文件里，中间没有任何一行代码看起来可疑。静态扫描器很难把这两点连起来。

所以现有的工具定位都是辅助，不是答案：

工具 类型 能做什么
NodeJsScan 静态扫描 标出 Node.js 代码中的可疑模式
Prototype Pollution Scanner 静态扫描 专门找易受污染的代码结构
PPFuzz 模糊测试 自动往输入点灌各种 payload
DOM Invader (Burp) 动态检测 客户端 source/sink 追踪
BlackFan 的客户端检测 参考实现 客户端原型污染的利用示范

它们能帮你缩小范围，但最终判断「这个参数会不会走到属性名的位置」，还是得靠人读代码。

这恰恰是这个漏洞类型值得单独学习的原因——它考的不是工具熟练度，是你对程序怎么运转的理解。

五、真实世界：它不只是一种理论

原型污染在真实世界里的战绩相当可观。

lodash 的三次补丁

lodash 是 npm 生态里被依赖最广的包之一（间接依赖它的包超过 15 万个），它因为原型污染被反复修补：

CVE 涉及函数 修复版本
CVE-2018-3721 _.merge / _.defaultsDeep 4.17.5
CVE-2019-10744 _.defaultsDeep 4.17.12
CVE-2020-8203 _.zipObjectDeep（及 _.set / _.setWith） 4.17.19

值得注意的是 CVE-2019-10744 是 CVE-2018-3721 修复不完整的绕过——第一次补丁只堵了 __proto__，攻击者改用 constructor.prototype 就绕过去了。这正好印证了上面说的：「必须三个 key 都拦」。

安全基线：lodash ≥ 4.17.21。

从污染到 RCE

原型污染最严重的后果是远程代码执行。原理是：Node 的 child_process 系列函数会从原型链上读取一些配置项，如果这些项没被显式赋值，攻击者污染的原型就会被读到。

最近的一次：CVE-2025-55182

2025 年 12 月披露的 CVE-2025-55182（”React2Shell”，CVSS 10.0） 是目前影响面最大的一次原型污染案例。

问题出在 React 的 Flight 协议反序列化逻辑：它没有校验传入的序列化数据，攻击者可以通过构造 "$1:__proto__:then" 这样的 key 污染 Object.prototype，再借助 "$1:constructor:constructor" 取到 Function 构造函数，最终通过 Function() 执行任意代码。无需认证，默认配置即可利用。

受影响范围包括 React Server Components 19.0.0 ～ 19.2.0，以及使用 App Router + Server Actions 的 Next.js 14.3.0-canary.77+、15.x、16.x。官方修复的方式，是把不安全的属性归属判断替换成 Object.prototype.hasOwnProperty.call(...)，并显式处理 __proto__——和上面「代码层防御」里写的是同一件事。

该漏洞已被 CISA 列入 KEV 目录并观测到在野利用。

六、附：靶场实操踩过的坑

以上内容来自 TryHackMe 的 Prototype Pollution 房间。把当时踩的坑记在这里，因为这些细节才是自己动手时真正卡住人的地方：

1. 专辑名必须一字不差。 触发 merge 的前提是 albumToClone 能找到。如果 selectedAlbum 的值和页面上真实的相册名对不上，函数会直接跳过，请求返回 200 但什么也没发生——看起来”payload 没生效”，实际是根本没进到漏洞代码。

2. 污染不会自己消失，只能重启。 Object.prototype 上的改动存在进程内存里。打完 toString 的 DoS 之后，进程已经挂了，此时不重启服务，下一个 payload 根本发不进去。做多轮测试时，每一轮之间都要重启。

3. 面板只认特定的属性名。 房间的验证面板按钮写着”检查是否有新属性”，但它实际只认它要找的那个名字。用别的属性名去试，会得到”属性还没添加”的提示——这不是利用失败，是判定逻辑不匹配。

4. 房间文案本身有笔误。 服务端代码片段里写的是 _.set(friend, input.path, payload.value)，但 payload 根本没有定义（应该是 input.value）。以实际回显为准，不要以题目文案为准——这在所有靶场里都成立。

5. 「原型污染」这个标签有时候是松的。 房间第一个 XSS 利用用的其实是 _.set 的任意路径写入（写 reviews[0].content），压根没碰 __proto__。看资料的时候要自己分清：改一个对象和改整个进程的原型，是两种不同的东西。

收尾

回到最开始那个 merge 函数。它没有 bug。

它只是安静地、忠实地执行了一件事：把 from 的每一个 key 写进 to。

而攻击者做的事也很简单：他没有改变任何一个值，他改变的是一个属性的名字。

这就是原型污染的全部内核——当你可以控制「属性名」，而不再只是「属性值」的时候，你控制的就不再是数据，而是程序的形状。
