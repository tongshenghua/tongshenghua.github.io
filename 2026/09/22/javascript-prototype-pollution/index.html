这篇文章是配合 TryHackMe 的 Prototype Pollution 房间写的：前面几节把原理从零讲清楚，最后一部分是房间里的实战记录。

对象里到底藏着什么

先从最普通的一个对象说起。

我写了两个属性，name 和 age。但有意思的是，下面这些也是能访问的：

我并没有写这两个东西。那它们是哪来的？

答案是：user 除了自己的属性，还挂着一个”备用的对象”。当你在 user 身上找不到某个属性时，JavaScript 会去那个备用对象里再找一遍。这个备用对象，就是原型（prototype）。

Object.getPrototypeOf() 是个静态方法，传一个对象进去，返回它的原型——所谓”静态”，是说它挂在 Object 构造函数自己身上，不在对象实例上（user.getPrototypeOf 是 undefined）。

所以 user 的原型就是 Object.prototype。toString 和 hasOwnProperty 都存在它上面，user 于是”继承”到了它们。

这里有个容易被忽略的点：原型不是一个对象私有的，是大家共用的。

两个完全不相干的对象，指向同一个原型对象。这就像两个人都把同一个抽屉当备用箱，你在里面放个东西，另一个人打开也能看到。

区别只在写法。__proto__ 更短，还能放在赋值号左边，所以更常见。

但有件事容易记错：__proto__ 不是 JavaScript 的关键字，它只是 Object.prototype 上的一个属性。这一点先放着，等下讲 JSON.parse 的时候回头看，会发现它是整件事的关键。

顺带说一句它的规范出身：__proto__ 定义在 ECMAScript 规范的 Annex B 里。那一章专门用来收纳历史遗留、为了兼容旧网页才保留的东西。换句话说，它本来就不该出现在现代代码里。

链子可以有很多层

原型本身也可以有原型，一层套一层，直到最顶上的 Object.prototype。看个例子：

ben 自己没有 introduce，但它继承了 person 的。

找属性的顺序是：先看 ben 自己，没有就往上找一层，还没有就再往上，直到找到或者走出链子。这条路径叫原型链。

链子的最顶端，就是前面那个共用抽屉。为什么每个对象最后都会连到它？因为用 {} 字面量建对象时，JavaScript 会直接把原型设成 Object.prototype。你随手敲的每个 {}，都在往同一个点上连。

那往这个点上写东西会怎样：

anything 是刚建出来的空对象，代码里没有人碰过它，但它读到了值——因为它和 a、和这个程序里所有其他的对象，连的是同一个点。

这就是原型污染：攻击者往原型链的共享节点上写数据。

那攻击者怎么才能写进去

到这儿你可能觉得，这不算漏洞啊——a.__proto__.name = 'x' 是我自己在控制台敲的，我想敲就敲，不想敲就不敲。

对。能访问 __proto__ 不是漏洞。漏洞出在”程序把用户输入写到了那个位置”。

问题在于，JavaScript 里有一类很常见的操作：把一串数据里的 key，当成属性名挨个写进另一个对象。这种写法本身没毛病，甚至可以说是必需品。但如果那串数据来自用户，性质就变了。

还有一条路：constructor.prototype

上面用的是 __proto__。但如果开发者把它过滤掉了呢？

JavaScript 里每个对象都能顺着 constructor 摸到自己的构造函数，再顺着构造函数的 prototype 摸到原型。对普通对象来说，obj.constructor 就是 Object，而 Object.prototype 正是我们要的那个共享节点。所以还有第二条路径：

历史上有过真实的教训：lodash 在 CVE-2018-3721 里补了 __proto__ 的洞，结果攻击者换成 constructor.prototype 就绕过去了，逼得官方在 CVE-2019-10744 里又补一次。这就是为什么”三个 key 都要拦”不是多此一举。

一个容易被忽略的细节

不过要老实说一句：这条路径能不能走通，取决于 merge 函数的类型判断。

上面那个 merge 里写的是 typeof to[key] == "object"。当 key 是 constructor 时，to["constructor"] 是 Object 这个函数——而 typeof 一个函数返回的是 "function"，不是 "object"：

条件不成立，于是走到 else 分支，把 constructor 当普通属性覆盖掉，不会递归，也就污染不了原型。

所以在这个房间的实现里，constructor.prototype 这条路是走不通的。但换成别的库——用 typeof x === 'object' || typeof x === 'function' 判断的、或者干脆不判断类型的——就未必了。

这也是原型污染排查的一个要点：光看”有没有过滤 __proto__“不够，还要看合并逻辑本身的类型判断怎么写。

为什么这个漏洞特别难防

merge 没错，qs 也没错，Object.prototype.toString 本身更没有错，它本来就是 JavaScript 语言的一部分。

攻击者污染的是一个所有人都在用的共享基础设施。他不需要知道 qs 的存在，只需要挑一个足够底层、足够通用的属性名去覆盖，剩下的交给调用链自己去撞。

这也解释了为什么静态扫描工具很难发现它。SQL 注入有拼接的固定特征，eval 有明确的关键字。而原型污染问的是：

用户能控制的字符串，最后有没有走到”属性名”的位置？

这是数据流问题，不是语法特征问题。同样一个 merge 函数，用在配置合并上完全安全，用在用户输入上就致命。工具没法从函数本身判断语境。

怎么防

分三层看，重要性依次递减。

根本解法：别让用户的名字走进属性名

合并之前把危险的名字过滤掉。 递归合并、深拷贝、路径赋值都适用：

三个都得拦。只拦 __proto__ 不够——很多库会递归进 constructor.prototype，lodash 就因此被打穿两次。

更彻底的做法是不给它原型。 Object.create(null) 建出来的对象没有原型链，污染够不着。纯当字典用的对象，也可以直接换成 Map。

缓解措施：改掉容易出事的习惯

判断属性别用点号和 in。 obj.someKey 和 'someKey' in obj 都会顺着原型链找，只有 Object.prototype.hasOwnProperty.call(obj, 'someKey') 是只认自己的。

遍历对象时优先用 Object.keys()。 它比 for...in 安全，因为不碰继承属性。

管好依赖

这个问题在 npm 生态里反复出现。npm audit 和 npm ls lodash 定期跑一跑。

lodash 是重灾区，历史上被连续打了三次补丁：

CVE 涉及函数 修复版本
CVE-2018-3721 _.merge / _.defaultsDeep 4.17.5
CVE-2019-10744 _.defaultsDeep（绕过上一次修复） 4.17.12
CVE-2020-8203 _.zipObjectDeep 4.17.19

安全线是 4.17.21。

常见绕过方式

防御措施 绕过方式
过滤 __proto__ 改用 constructor.prototype
过滤字符串 key 用数组形式 ["__proto__"]
只过滤第一层 深层嵌套 {"a": {"__proto__": {...}}}
只过滤 JSON 输入 改用 URL 参数 ?__proto__[x]=1
只过滤 __proto__ 和 constructor 检查是否还漏了 prototype 本身

防御 Checklist

  • 所有接收用户输入的对象写入，都过滤 __proto__ / constructor / prototype
  • 只做数据容器的对象，用 Object.create(null) 或 Map
  • 判断属性存在性统一用 Object.prototype.hasOwnProperty.call()
  • 遍历对象优先用 Object.keys() / Object.entries()，而不是 for...in
  • child_process 的 shell / env / execArgv 全部显式传值
  • 进程启动参数加 --disable-proto=delete
  • 定期 npm audit，lodash 保持在 4.17.21 以上

几个踩过的坑

记下来，因为这些细节才是自己动手时真正卡住人的地方。

专辑名必须一字不差。 触发 merge 的前提是能通过相册名找到目标对象。名字对不上，函数直接跳过，请求返回 200 但什么都没发生。看起来像 payload 没生效，其实是压根没走进漏洞代码。

污染不会自己消失，只能重启。 Object.prototype 上的改动存在进程内存里。打完 DoS 之后进程已经死了，不重启服务，下一个 payload 根本发不进去。做多轮测试时每一轮之间都要重启。

“原型污染”这个标签有时候用得比较松。 房间里第一个 XSS 利用用的是 _.set 的任意路径写入，压根没碰 __proto__。看资料的时候要自己分清：改一个对象，和改整个进程的原型，是两种不同的东西。

房间文案本身有笔误。 服务端代码片段里写的是 _.set(friend, input.path, payload.value)，但 payload 根本没定义，应该是 input.value。以实际回显为准，不要以题目文案为准，这在所有靶场里都成立。

最后

回到开头那个 merge 函数。它没有 bug。

它只是老实地执行了一件事：把 from 的每个 key 写进 to。

攻击者做的事情也很简单：他不改任何值，他改的是属性的名字。

而一个名字，就足够让全站的 isAdmin 变成 true，让每个请求都在解析查询字符串时崩掉。

一句话记住它：原型污染不改变任何值，它改变的是属性的名字。
